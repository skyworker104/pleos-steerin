# 주차 위치 점수 (SVM 연동 확장) 기술 검토 및 구현 (2026-11-08)

## 1. 요약
* 현재 100점은 **과정 점수**다. 조향·재시도·속도·안전·시간을 본다.
* 서라운드 뷰 모니터(SVM)가 있는 차량은 이미 차량 안에서 주차선과 주차칸을 인식한다. Pleos가 그 **인식 결과 숫자**를 공개하면 "어디에 세웠는가"를 평가하는 **위치 점수**를 더할 수 있다.
* 앱은 이 확장을 미리 구현했다. 데이터 소스 인터페이스, 위치 채점기, 결과 화면의 위에서 본 도식, 이력 저장, 단위 테스트까지 완료. 남은 일은 SVM 데이터 소스 구현체 1개다.
* 현재 플랫폼에는 SVM 데이터가 없으므로 운영 기본값은 "위치 점수 없음"이다. 시연용 가상 데이터는 스위치로만 켜지고, 화면과 이력에 항상 "가상 데이터"로 표시된다.

## 2. Pleos에 요청하는 데이터
원본 카메라 영상이 아니라 인식 결과만 요청한다. 숫자 몇 개는 얼굴·번호판 같은 개인정보가 없고, 앱의 연산 부담도 없다.

| 필드 | 단위 | 정의 |
| :-- | :-- | :-- |
| `leftGapCm`, `rightGapCm` | cm | 차체 측면 ~ 해당 쪽 주차선. 음수는 선 침범 |
| `frontGapCm` | cm | 앞 범퍼 ~ 주차칸 입구선. 음수는 차 앞이 칸 밖 |
| `rearGapCm` | cm | 뒤 범퍼 ~ 끝선 또는 스토퍼 |
| `yawDeg` | ° | 차량 중심축 대 주차칸 중심축 |
| `confidence` | 0~1 | 인식 신뢰도 |
| 시점 | ms | P 체결 시각의 최신 값 |

코드: `domain/outcome/SlotOutcome.kt`의 `SlotObservation`.

## 3. 위치 점수 (100점)
| 항목 | 배점 | 만점 | 0점 |
| :-- | :--: | :-- | :-- |
| 주차선 안 | 30 | 네 간격 모두 0 이상 | 어느 쪽이든 10cm 초과 침범. 10cm 이내 침범은 15점 |
| 좌우 균형 | 30 | 좌우 차이 10cm 이하 | 60cm 이상, 사이는 선형 |
| 앞뒤 깊이 | 20 | 앞이 입구선 안, 뒤 여유 10~50cm | 앞이 입구선 밖, 또는 범위에서 40cm 이상 벗어남 |
| 평행 정렬 | 20 | 기울기 1.5° 이하 | 8° 이상, 사이는 선형 |

* 신뢰도 0.6 미만이면 위치 점수를 만들지 않는다. 잘못된 감점보다 미표시가 낫다.
* **종합 점수** = 과정 70% + 위치 30% (반올림). 위치 점수가 없으면 과정 점수가 그대로 종합 점수다. 등급은 종합 점수로 정한다.
* 다음 주차 팁은 과정 5개·위치 4개 항목 중 달성률이 가장 낮은 항목에서 고른다.
* 임계값은 `SlotOutcomeEvaluator.Config` 한 곳에 있다.

## 4. 앱 구조
```
data/outcome/ParkingOutcomeSource.kt
  ParkingOutcomeSource        observeAtPark(ParkEvent) → SlotObservation?
  UnavailableOutcomeSource    운영 기본값 (오늘의 Pleos: 항상 null)
  SimulatedOutcomeSource      시연 전용, 과정 점수 구간별 고정 예시값 3종
domain/outcome/
  SlotOutcome.kt              SlotObservation · OutcomeScore · OutcomeCategory
  SlotOutcomeEvaluator.kt     위치 채점 + 종합 점수
presentation/
  ParkingViewModel            P 체결 → 슬롯 조회 → 위치 채점 → 화면·음성·저장
  ui/ResultScreen             종합/과정/위치 점수, 위에서 본 도식, 위치 항목 막대
  ui/StandbyScreen            "SVM 위치 점수 시연" 스위치 (기본 꺼짐)
  ui/HistoryScreen            종합 점수, "과정 n · 위치 m · 가상 데이터"
domain/session/SessionCodec   선택 헤더 `slot=…` (구버전 파일 그대로 읽힘, 깨진 slot 줄은 무시)
```
SVM이 공개되면 `SteerinApplication.outcomeSource`를 SVM 구현체로 바꾸는 것 외에는 바뀌는 곳이 없다.

## 5. 시연용 가상 데이터
* 과정 점수 85 이상, 65 이상, 그 미만에 각각 고정 예시값을 돌려준다. 측정치가 아니며, "매끄러운 과정이면 위치도 좋다"는 시연용 대응이다.
* 결과 화면 배지, 이력 행에 항상 "가상 데이터"로 표시한다. 저장 파일에도 `source=SIMULATED`가 남는다.

| 예시 | 좌 | 우 | 앞 | 뒤 | 기울기 | 위치 점수 |
| :-- | --: | --: | --: | --: | --: | --: |
| 과정 85+ | 41 | 37 | 32 | 24 | 0.8° | 100 |
| 과정 65~84 | 28 | 52 | 12 | 44 | 2.6° | 89 |
| 과정 65 미만 | 14 | 66 | −6 | 62 | 4.4° | 31 |

## 6. 검토 후 배제한 대안: 화면 주기 캡처
API 없이 후방 카메라 화면을 캡처해 주차선을 인식하는 방식을 Pleos_Connect_v2.1 AVD에서 검토했다.

| 확인 항목 | 결과 |
| :-- | :-- |
| 화면 캡처 동의 화면 (`MediaProjectionPermissionActivity`) | 시스템 UI에 존재. 캡처 API는 쓸 수 있을 가능성이 높음 |
| 카메라 창 보호 플래그 (FLAG_SECURE) | 없음. 캡처하면 카메라 영상이 찍힐 것으로 보임 |
| 카메라 직접 접근 (`USE_CAR_EVS_CAMERA`) | signature/privileged 권한. 서드파티 불가 |
| 에뮬레이터 카메라 영상 | 고정 도로 주행 영상 + 측면 영상. SVM 탑뷰와 주차선 없음 |

배제 이유:
1. **개인정보**: 행인 얼굴, 다른 차 번호판이 캡처된다. 저장하지 않아도 수집 자체가 심사·마켓 정책 위험.
2. **매번 동의**: Android 14는 캡처 세션마다 동의가 필요하다. 주차할 때마다 팝업은 실사용 불가.
3. **화면 구성 의존**: 카메라 앱 배치는 차종·트림·OTA마다 바뀐다. SVM 탑뷰가 없는 트림은 원근 영상뿐이라 좌우 간격 정확도가 크게 떨어진다.
4. **시연 불가**: 에뮬레이터 영상에 주차선이 없다.
5. **효과 제한**: R 구간에는 서드파티 화면이 차단되므로(`docs/CAMERA_POPUP_REVIEW.md`) 결국 음성으로만 전달된다.
6. **심사 인상**: 기술 활용성은 Pleos API 활용을 본다. 시스템 앱 화면 긁기는 반대로 읽힐 수 있다.

연산 성능은 문제가 아니다. 탑뷰는 이미 평면 보정돼 있어 초당 1~2장, 축소 이미지의 흰 선 검출로 간격을 대략 추정할 수 있다. 즉 "불가능해서"가 아니라 "개인정보·정책·유지보수 이유로" 배제했다.

## 7. 검증
* 단위 테스트 9건 추가 (`SlotOutcomeEvaluatorTest` 8, `SessionCodecReplayTest` 1). 전체 33건 통과.
* Pleos_Connect_v2.1 AVD 실측: 스위치 켬 → Virtual Console 모범/초보 주차 → 결과 화면 위치 도식·종합 점수·이력 표시 확인. 스크린샷 `docs/screenshots/12~15`.
* release APK에서도 스위치 기본값은 꺼짐. 켜지 않으면 동작은 이전과 같다.
